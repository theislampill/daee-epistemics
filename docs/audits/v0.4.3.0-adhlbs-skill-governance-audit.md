# v0.4.3.0 ADHLBS Skill Governance Audit

## Executive verdict

TARGETED ADHLBS ADDITIONS NEEDED

ADHLBS is useful as an external governance reference, not as runtime source. The repo already
covers most of its high-value skill-engineering discipline through `AGENTS.md`, operating
discipline docs, generated-runtime manifests, owner-file frontmatter, static checkers, and the
v0.4.3.0 Smoke E/F A/B loop. The v0.4.3.0-safe additions are limited to a compact `AGENTS.md`
reference-audit rule, a short operating-discipline note for read-only/cite-or-retract/context
budget behavior, and this audit record.

No `SKILL.md` entrypoint prose is added in this pass. Trigger-eval taxonomy and skill retirement
criteria are real gaps, but they should be designed as owner/checker work after v0.4.3.0 rather
than squeezed into the runtime entrypoint before merge/release.

## Reference basis

Inspected the live ADHLBS page at https://theislampill.github.io/adhlbs/ on 2026-05-19. Relevant
sections/directives:

- Universal default: `RTFM -> TRACE -> OWNER -> SSOT -> ATOMIC PATCH -> VERIFY`.
- `STACK-AGENT-01`: `SKILL ENG -> PROGRESSIVE DISCLOSURE -> TRIGGER EVALS -> STRUCTURED OUTPUT -> EVAL HARNESS`.
- `STACK-PROMPT-01`: `REQUIREMENTS -> PROMPT -> EVAL -> VERSION -> DEPLOY -> MONITOR`.
- `STACK-SKILL-01`: `TRIGGER -> LOAD -> EXECUTE -> EVAL -> REVISE -> RETIRE`.
- Agent controls: Plan + Persist, Tool Policy, Read-Only First, Context Budget, Quote-First
  Grounding, Cite or Retract.
- Skill notes: manifest fields, progressive disclosure, should-trigger/should-not-trigger/
  ambiguous-trigger/regression evals, no skill mutation without receipt, coordinator verifies.
- `PACK-SKILL-STRICT`: manifest, concise trigger description, lean core, references/scripts,
  permissions, typed outputs, trigger evals.

## P1 / later

- Trigger eval taxonomy: create a small owner manifest or fixture convention that names
  should-trigger, should-not-trigger, ambiguous-trigger, and regression cases without scanning all
  prose or hardcoding model phrasing.
- Skill lifecycle/retirement rule: define when a module/trigger/owner is revised, retired, or kept
  as historical evidence. This should live with module catalogue/frontmatter governance, not in
  `SKILL.md`.
- Optional checker: add only after the trigger/lifecycle owner shape exists and can be kept
  low-noise.
- Formalism pointer matrix generation: only if manual symbol ledgers drift. The current
  v0.4.3.0 formalism pointer audit found source ownership clean and no missing runtime cue.

## Do-not-add

- Do not import the whole ADHLBS sheet into repo docs.
- Do not add ADHLBS prose to `atomics/skill/SKILL.md`; no entrypoint-critical runtime invariant was
  missing from this audit.
- Do not add a broad global prose checker that punishes theory, case-library, or explanatory docs.
- Do not treat local inlined generated-runtime smoke as package-bound release-smoke proof.
- Do not add promptware lifecycle ceremony unless prompt packs become maintained repo artifacts.

## Smoke/check impact

The original ADHLBS governance patch did not change runtime semantics or `atomics/skill/SKILL.md`
content, so Smoke E/F remained sufficient for that patch. The later formalism-pointer follow-up
did run Smoke G/H with the corrected inlined generated-runtime method; both phases passed 6/6 and
are recorded below and in `docs/audits/v0.4.3.0-formalism-pointer-discipline-audit.md`. None of
these local generated-runtime smokes is package-bound release-smoke proof.

## Specific audit answers

1. Trigger eval coverage exists partially through trigger matrix data, routing/reconstruction
   fixtures, and smoke cases, but the explicit should-trigger/should-not-trigger/ambiguous-trigger/
   regression taxonomy is not fully formalized.
2. Retire-or-revise criteria are not explicit enough for skill/module lifecycle governance. This is
   P1/later unless a v0.4.3.0 release blocker appears.
3. The current local generated-runtime smoke process verifies load/execute/eval behavior when the
   generated runtime is inlined. It does not verify retire/defer lifecycle and is not package-bound
   release proof.
4. `SKILL.md` still satisfies progressive disclosure: lean core, owner pointers, generated runtime
   boundary, and references/scripts only when needed.
5. Plan Closure is enforced in current audits through done/changed/blocked/deferred/unverified
   closure tables.
6. Smoke Before Claim is enforced for local generated-runtime evidence and checker-only claims; the
   package-bound release evidence boundary remains intentionally separate.
7. Tool Policy, Read-Only First, Context Budget, Quote-First, and Cite-or-Retract are now present
   enough for repo agents in the operating-discipline doc without bloating `AGENTS.md`.
8. The missing high-value checker is a future low-noise trigger-eval/lifecycle checker, but it needs
   an owner manifest first.

## Formalism pointer-discipline follow-up

Follow-up audit: `docs/audits/v0.4.3.0-formalism-pointer-discipline-audit.md`.

Result: FORMALISM POINTERS CLEAN. The formal notation already maps to source ownership:
`diagnostic-ir.md` owns IR/register bridge semantics, `recursive-state-transitions.md` owns
reread/field-operator semantics, render/output owners govern visibility and release, docs/index
runtime architecture is a generated source projection, and checker tools act as controllers. The
new `AGENTS.md` rule keeps SOLID / GRASP / CUPID / ACID / BASE as pointer discipline only.

Follow-up PDCA result: Smoke G/H were run with the corrected inlined generated-runtime method after
the formalism-pointer request. G and H both passed 6/6 with first-visible `field:` lines, preserved
formal notation, preserved non-claim boundaries, and no `SKILL.md` runtime prose or runtime
semantic change. The only implementation change was a local smoke-validator hardening so
`formalism-smoke-*` phases are discovered and G5/G6/H5/H6 style notation-preservation cases fail
on ASCII simplification or placeholder drift.
