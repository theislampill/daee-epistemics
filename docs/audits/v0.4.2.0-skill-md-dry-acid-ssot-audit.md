## DRY findings

- INTENTIONAL SAFETY DUPLICATE: the canonical compact DSL surface, Layer A / Layer B split,
  `Land(B) -> R(H,Delta)`, STOP/HOLD/PARTIAL/RECURSE, source-owner execution, owner-body access,
  and release-smoke witness mode remain repeated because models often load only `SKILL.md`.
- SHOULD BE POINTER: detailed Phase 2 pass list, hard compound source-request examples, and
  minimum execution load floor are near the line between entrypoint gate and owner manual.
- SHOULD MOVE OUT: no P0 move-out item. Moving hard-case examples now would risk runtime behavior.
- STALE / CONFLICTING: no direct stale release-smoke wording found. The only unclear owner is the
  task-named `runtime-output-governance.md`, which is absent; current owner responsibilities are
  split across existing render/release/recursive files.

## ACID findings

- Atomicity: a cleanup pass should only edit `atomics/skill/SKILL.md` plus owner files it points to,
  then rebuild generated `skill/**`; this audit does not mutate runtime semantics.
- Consistency: generated `skill/SKILL.md` must be checked with
  `python tools/check_compiled_runtime_freshness.py`. Generated length is expected to differ from
  atomics source because of compiler-injected material.
- Isolation: any P1 pointer patch should be semantics-neutral and must not alter release-smoke
  witness mode, default render mode, owner-body access, or package behavior.
- Durability: future shrinkage should be paired with checker or fixture coverage for the exact
  invariant removed from the always-loaded entrypoint.

## Progressive-disclosure findings

`SKILL.md` is long for an always-loaded entrypoint, but it is not a progressive-disclosure failure.
Most later sections are routers/pointers. The risky density is concentrated in hard-case execution
floor, detailed pass/load floor, and repeated default-render language.
