## What CI Should Not Decide

- Hard schema/register migration: the schema-light register bridge remains schema-light unless the maintainer approves a
  full producer/consumer/schema/fixture migration. CI should verify current bridge behavior, not
  force hard fields.
- Deleting or archive-moving historical docs: historical docs may feel current, but this is a
  documentation lifecycle/indexing problem, not a build failure.
- Checker helper consolidation: checker sprawl is a controlled maintenance risk; CI should not
  require a shared helper until drift or bugs justify extraction.
- Untracking generated `skill/**`: generated runtime currently supports release/package inspection.
  CI should enforce freshness, not remove the generated tree.
- Prompt-specific secularcompact/TST burden templates: those are regression canaries and audit
  evidence, not universal runtime doctrine.
- Treating ignored local smokes as package/release proof: `.daee/`, `smokes/`, and retained local
  samples are evidence only when explicitly classified, and package/release proof requires package
  filename/SHA provenance.

## Release Artifact Automation Design

Expected release path:

```text
atomics/skill/**
-> python tools/build_framework_pipeline.py
-> python tools/build_compiled_runtime.py
-> skill/**
-> python tools/package_skill.py build/daee-epistemics-<version>.skill.zip
-> copy/rename checked payload to build/daee-epistemics-<version>.skill
-> SHA256 / size / entry-count metadata
```

Requirements:

- The release workflow must build from atomics, not package a stale `skill/**` snapshot.
- The package archive must not contain `atomics/`, `tools/`, `docs/`, `build/`, `.git/`, or a
  top-level `skill/` wrapper.
- Archive root must contain `SKILL.md`, `README.md`, `references/`,
  `compiled-module-map.json`, and `build-manifest.json`.
- Generated dev harness roots `data/`, `scripts/`, and `tests/` must remain excluded from the
  canonical package unless a separate dev artifact is deliberately designed.
- `workflow_dispatch` artifact build may upload the checked `.skill` as a workflow artifact.
- GitHub Release upload should happen only on tag push or explicit approved release path.
- The GitHub Release asset should be `.skill` only. Do not upload `.skill.zip` to the release.
- `docs/release-artifacts.md` currently records v0.4.0.0 metadata. Automation should either:
  - emit metadata and leave docs update as a manual reviewed source commit; or
  - in a later approved release-doc automation phase, open a PR/commit updating artifact docs.
  It should not silently mutate release docs from push/PR CI.

## Conway/YAGNI Guardrails

- Generated `skill/**` must not become source of truth: CI should rebuild it from atomics and fail
  if the generated tree drifts.
- Checker sprawl must not be frozen: add py_compile and existing invariant checkers first; do not
  create CI jobs around every historical incident.
- Secularcompact/TST must not become runtime templates: use structural render/banner and
  recursive-state invariants, not prompt-specific burden lists.
- `docs/index.html` and algebraic notation are not runtime source: CI may check known docs tokens
  through existing checkers, but source ownership stays in atomics and tools.
- Historical docs should not be treated as current merely because CI can scan text. Use release-marker
  sweeps narrowly and leave historical-doc lifecycle to docs policy.
- Root `SKILL.md` must not expand again: metacompliance drift budget and owner-token checks stay in
  push/PR CI.
- Hard schema/register fields must not be added to simplify automation. CI checks register-formalism bridge
  behavior under the schema-light baseline.

## Risks

- GitHub Actions release permissions: release upload requires `contents: write`; push/PR CI should
  remain read-only.
- Tag/release mismatch: automation must check intended tag, source commit, and GitHub Release target
  before upload.
- `.skill` vs `.skill.zip`: package script emits `.skill.zip`, but GitHub Release should receive
  the checked renamed `.skill` asset only.
- Artifact duplication: workflow artifacts and GitHub Release assets are different surfaces; avoid
  uploading both `.skill` and `.skill.zip` to the release.
- Generated runtime drift: release workflow must rebuild and fail on dirty generated diff before
  packaging.
- Release docs SHA drift: package metadata in docs can become stale if artifacts are rebuilt without
  a reviewed docs update.
- CI runtime cost: current push/PR CI already runs many Python structural checks; adding archive
  build should be release-only unless cost is acceptable.
- Over-enforcement of local smoke artifacts: ignored `.daee` and docs/smoke artifacts should not be
  required for every push/PR.
- Checker sprawl: adding one job per incident would encode historical repair sequence rather than
  stable invariants.
