## Finding

The normal CI workflow has already been moved to Node 24-compatible action
pins, but the manual release artifact workflow still carries older action pins:

- `.github/workflows/release-skill.yml`: `actions/checkout@v4`;
- `.github/workflows/release-skill.yml`: `actions/setup-python@v5`;
- `.github/workflows/release-skill.yml`: `actions/upload-artifact@v4`.

Pages run `26734688455` and later Pages run `26734835377` both passed while
emitting a Node.js 20 action deprecation annotation that named
`actions/checkout@v4` and `actions/upload-artifact@v4`.

## Current Boundary

This is release-gate-adjacent workflow source. It is not an ordinary
owner-free checker/fixture lane because the workflow builds and uploads skill
and provenance artifacts when dispatched.

Current state:

- `.github/workflows/ci.yml` uses `actions/checkout@v5` and
  `actions/setup-python@v6`.
- `.github/workflows/release-skill.yml` still uses the older pins above.
- No package/release/provenance lane is open.
- No workflow dispatch is authorized by this packet.

## What A Maintenance Lane Would Change

If accepted, the narrow maintenance lane would:

1. verify the currently supported Node 24-compatible major versions for the
   three release-workflow actions;
2. update only the action pins/defaults needed for Node 24 compatibility;
3. leave release workflow semantics unchanged;
4. run static/source checks only;
5. not dispatch the release workflow and not build or upload artifacts.

The lane should not modify package-building logic, provenance payload logic,
release asset names, release notes, tags, GitHub Releases, runtime source,
schemas, checkers, fixtures, or retained proof corpus artifacts.

## Risks

- Updating action pins without checking current upstream compatibility can
  replace a known warning with an unknown release-workflow failure.
- Running the workflow would build package/provenance artifacts and cross the
  protected release/provenance boundary.
- Treating a workflow-pin update as proof would overclaim; it is maintenance,
  not runtime/proof-corpus evidence.
- Changing package/provenance steps while touching action pins would mix a
  maintenance lane with release behavior.

## Required Checks If Accepted

Use static and source-boundary checks only unless the owner separately opens a
release/provenance gate:

```powershell
git diff --check -- .github/workflows/release-skill.yml
python tools\build_docs_index.py --check
rg -n "actions/checkout@v4|actions/setup-python@v5|actions/upload-artifact@v4" .github\workflows\release-skill.yml
```

Before commit/push, also run the usual staged forbidden-path and staged
secret/private scans. Do not run `workflow_dispatch` for `release-skill.yml`
inside this maintenance lane.

## Owner Options

1. Accept a no-package release-workflow action-maintenance lane.
2. Defer action maintenance until the next explicit release/provenance prep
   gate.
3. Reject a standalone maintenance lane and require release-workflow action
   changes to be bundled only with a future full release-gate preflight.

## Recommendation

Recommend option 1, but only as a no-package source-maintenance lane. It
removes a known future GitHub Actions compatibility warning before the next
release gate, while preserving the boundary that no package, tag, upload,
GitHub Release update, provenance publication, A.13 follow-on, full IR decode,
D.8 cleanup, or model-smoke campaign is opened.
