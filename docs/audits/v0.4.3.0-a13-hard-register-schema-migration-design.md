# A.13 Hard Register Schema Migration Design

Status: `DESIGN_PROPOSED / USER_ACCEPTANCE_REQUIRED`

This document is a design gate for A.13. It does not authorize a hard
Diagnostic IR schema patch. The current v0.4.3.0 proof surface remains
schema-light until the orchestrator explicitly opens a schema migration lane.

## Purpose

A.13 promotes the register set currently inferred by the schema-light bridge
into canonical Diagnostic IR fields:

- `heart` / `♥`
- `xi` / `ξ`
- `Omega` / `Ω`
- `mu` / `μ`
- `kappa` / `κ`

The migration exists to make A.10 NLA isomorphism, A.11 normalized activation
records, A.12 reproducibility, and B.5 IR-state decode machine-checkable at the
register-state level.

## Non-Goals

- Do not claim interlocutor uptake or soul access.
- Do not make Graphify or ActiveGraph proof authorities.
- Do not replace existing checkers with schema validation alone.
- Do not make legacy schema-light artifacts silently satisfy the hard-register
  contract.
- Do not open release/provenance, package, tag, upload, or release-note work.

## Versioning Plan

Introduce a new Diagnostic IR schema version marker before requiring hard
register fields. The new version must be distinguishable from current
schema-light artifacts.

Required version behavior:

- Current schema-light artifacts remain valid only under their existing
  contract.
- Hard-register artifacts must declare the new schema version explicitly.
- A schema-light artifact that claims the hard-register version must fail.
- A hard-register artifact that omits any canonical register object must fail.
- Checkers that consume field witness data must branch on the declared schema
  version rather than assuming all historical smokes have hard register fields.

## Canonical Field Location

Preferred shape inside Diagnostic IR:

```json
{
  "diagnostic_ir_schema_version": "0.4.3-hard-registers-v1",
  "registers": {
    "heart": { "state": "non_live", "functions": [], "basis": [], "non_live_reason": "not-diagnosed" },
    "xi": { "state": "live", "functions": ["warrant-authority"], "basis": ["..."] },
    "Omega": { "state": "live", "functions": ["ontology-predication"], "basis": ["..."] },
    "mu": { "state": "live", "functions": ["memetic-carrier"], "basis": ["..."] },
    "kappa": { "state": "live", "functions": ["dependency-collapse"], "basis": ["..."] }
  }
}
```

The field names above intentionally keep ASCII aliases (`heart`, `xi`,
`Omega`, `mu`, `kappa`) as machine keys. Glyphs remain accepted display labels
only.

## Register Object Contract

Every register object must include:

- `state`: one of `live`, `held`, `non_live`.
- `functions`: controlled tokens explaining the structural role when the
  register is `live` or `held`.
- `basis`: one or more evidence strings or source-local references when the
  register is `live` or `held`.
- `non_live_reason`: required when `state = non_live`.

Checker implication:

- `live` and `held` registers create explicit burden-floor obligations.
- `non_live` registers do not create burden-floor obligations, but must explain
  why the register is not in play.
- `held` does not satisfy completion by itself; it must be represented as
  HOLD/PARTIAL/non-load-bearing with a reason.

## Initial Controlled Vocabulary

This vocabulary should start deliberately small and expand only when fixtures
prove the need.

| Register | Required structural meaning | Initial function tokens |
|---|---|---|
| `heart` / `♥` | affective/posture burden | `affective-posture`, `security-posture`, `moral-recoil`, `restoration-recoil` |
| `xi` / `ξ` | warrant/authority burden | `warrant-authority`, `source-order`, `proof-tribunal`, `testimony-status` |
| `Omega` / `Ω` | ontological/predication burden | `ontology-predication`, `category-transfer`, `referent-confusion`, `creator-creation` |
| `mu` / `μ` | memetic carrier burden | `memetic-carrier`, `compression-carrier`, `defensive-stabilizer`, `mutation-reproduction` |
| `kappa` / `κ` | dependency/collapse burden | `dependency-collapse`, `entailment-chain`, `closure-boundary`, `cycle-curl` |

The `mu` register keeps its existing specificity rule: a live `mu` burden must
perform carrier decomposition, including which `Omega`, `xi`, or `kappa`
pressures the carrier packages.

## Field Witness Reconciliation

Hard-register Diagnostic IR must reconcile with current field witness surfaces:

- `coverage_proof.diagnostic_completeness.live_registers` must equal the live
  or held register set derived from `registers`.
- `coverage_proof.diagnostic_completeness.coverage` must show at least one
  burden-floor entry covering every live or held register, unless a register is
  explicitly non-load-bearing with proof.
- `field_witness.normalized_activation_record.live_registers` must equal the
  same canonical register set.
- `field_witness.normalized_activation_record.per_burden[].generation_depth`
  remains the structural depth slot for A.10/A.12 comparison.
- `field_witness.generated_burdens[]` and B.1/B.2 certificate fields remain the
  graph proof surface; the register schema does not replace them.

## Checker Migration Slices

Patch lanes must remain sequential unless a separate git worktree is created.

1. Schema design acceptance:
   - Accept or revise this document.
   - No runtime/schema behavior change.
2. Dual-version schema parser:
   - Update `atomics/skill/references/diagnostics/diagnostic-ir.schema.json`.
   - Update generated `skill/` copy only through the normal runtime build.
   - Keep schema-light support version-gated.
3. Integrity checker migration:
   - Update `tools/check_ir_instance_integrity.py` to enforce the hard-register
     object only when the hard schema version is declared.
   - Replace or narrow the current anti-hard-register guard in
     `tools/check_register_formalism_bridge.py` so it still rejects accidental
     hard fields in schema-light versions.
4. Field witness / convergence migration:
   - Update `tools/check_field_witness_convergence.py` to derive live register
     obligations from the canonical `registers` object when present.
   - Keep schema-light extraction for legacy/focused fixtures.
5. Reproducibility and NLA migration:
   - Update `tools/check_reproducibility.py` to compare canonical register
     objects through normalized activation records.
   - Update `tools/check_nla_decode_semantic_faithfulness.py` only after the
     register object is available as a trusted decode input.
6. Runtime emission:
   - Update Diagnostic IR guidance and compiled runtime source to emit the hard
     register object for governed outputs under the new schema version.
7. Smoke proof:
   - Run a fresh three-output governed reproducibility smoke with canonical
     register objects and `normalized_activation_record`.
   - Re-run B.1/B.2/B.5 validators on the accepted artifacts.

## Required Fixtures and Canaries

Positive fixtures:

- One minimal hard-register artifact with all five register objects present and
  only `xi` live.
- One mixed live-register artifact covering `Omega`, `xi`, `mu`, and `kappa`.
- One `heart` live/held artifact proving affective/posture coverage.
- One `mu` live artifact proving carrier decomposition and carried
  `Omega`/`xi`/`kappa` pressures.

Negative canaries:

- Hard schema version declared while one register object is missing.
- Live `kappa` with no dependency/collapse burden coverage.
- Live `xi` with no warrant/source-order burden coverage.
- Live `mu` with no `mu`-typed burden and no explicit non-load-bearing proof.
- Live `mu` with a generic operation that does not decompose a carrier.
- `collapse_complete = true` while a live or held register is unresolved.
- Schema-light artifact falsely claiming the hard-register schema version.
- Hard-register artifact using display glyphs as machine keys instead of
  canonical ASCII keys.

## Stop Conditions

Stop before patching runtime/schema/checker behavior if:

- the register object shape is not accepted;
- a migration would require weakening current schema-light checkers;
- legacy artifacts cannot be version-gated cleanly;
- the dirty worktree contains conflicting changes in schema/checker families;
- the next patch would require package/release/provenance work.

## Acceptance Gate

This design moves A.13 from `BLOCKED: design missing` to
`BLOCKED: awaiting user acceptance of migration design`.

The next implementation lane may open only after the orchestrator records
explicit acceptance and names one concrete patch slice, allowed files, fixtures,
commands, and stop condition.
