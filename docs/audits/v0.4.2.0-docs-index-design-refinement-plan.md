# docs/index Design Refinement Plan

## Executive verdict

TARGETED REFINEMENT NEEDED

The current docs/index surface is acceptable as a generated, source-aware
navigation aid. It has no observed P0 visual blocker in the desktop browser pass:
the Architecture carousel is selected-primary, the paired Architecture pipelines
do not create page-wide overflow, Theory notation wraps, and the page-level
horizontal overflow check is clean.

The design is still not materially refined enough to be treated as a public
showcase. The main problem is not missing runtime semantics. It is visual
hierarchy: too many surfaces use the same dark card/table language, provenance
and audit tables can dominate the human reading path, and support tabs need
stronger progressive disclosure. This should be fixed through source-owned
tokens, component contracts, generator changes, and non-brittle checker guards,
not by hand-editing generated HTML.

## 5 Whys

### 1. Reference Library is table-first

1. Why does this look or feel bad? The first meaningful Reference object is a
   106-row table, so the human task of browsing or selecting a source document
   is buried below an auditor surface.
2. Why did the generator/checker allow it? The generator correctly emits all
   reference rows, and the checker validates source parity, but neither checks
   the default reading order or the height of raw source maps.
3. Why did DESIGN.md not prevent it? It says source/provenance material should be
   secondary, but it does not define a Reference-specific hierarchy where summary,
   list, selected preview, and raw table have distinct roles.
4. Why did visual QA not catch or prioritize it? The prior QA emphasized
   Architecture carousel, Theory notation, page overflow, and interaction
   regressions. It did not measure support-tab table dominance.
5. What prevents recurrence? Add a Reference component contract in `DESIGN.md`,
   render a summary/list/detail source browser before the raw table, place the
   raw table in disclosure, and add checker coverage that a default-visible
   Reference raw table cannot be the first dominant object.

### 2. Owners & TTP becomes an auditor wall

1. Why does this look or feel bad? The tab starts with useful interaction, then
   becomes thousands of pixels of matrix/source tables that make the operator
   model feel less legible than it is.
2. Why did the generator/checker allow it? The generator emits catalogue-backed
   rows inline, and the checker proves rows are not stale. It does not enforce
   progressive disclosure thresholds for large audit material.
3. Why did DESIGN.md not prevent it? The provenance rule focuses on Architecture
   and Theory default reading paths; it leaves Owners/Reference support surfaces
   under-specified.
4. Why did visual QA not catch or prioritize it? The pass verified interaction
   and parity, not whether the full tab height and table order fit the human
   workflow.
5. What prevents recurrence? Define Owners as a selected-detail workspace with
   collapsed full audit tables, add source-derived summary counters, and update
   the checker to require interactive operator/family controls before raw
   matrix/source tables.

### 3. The site still feels visually flat

1. Why does this look or feel bad? Many surfaces use the same dark panel,
   border, chip, and compact heading pattern, so focal objects and support
   evidence have similar weight.
2. Why did the generator/checker allow it? Token checks confirm source-owned
   colors and dimensions, but do not know which component role is primary,
   secondary, control, provenance, or raw data.
3. Why did DESIGN.md not prevent it? It added important "do not" rules, but not
   a mature component inventory with role-specific examples.
4. Why did visual QA not catch or prioritize it? A page can have no overflow,
   no clipped cards, and intact interactions while still lacking hierarchy.
5. What prevents recurrence? Add role tokens and component contracts to
   `DESIGN.md`, emit `data-surface-role` or equivalent classes from source
   templates, and include a screenshot question for every tab: "what is the one
   primary focal object and what is deliberately secondary?"

## Recommended refinement roadmap

### P0

No current P0 visual blocker was observed. Do not block v0.4.2.0 solely on this
plan if the release goal is a safe source-aware docs/index surface rather than a
polished showcase.

### P1

- Add component role taxonomy and role-owned visual tokens for focal, support,
  control, provenance, and raw-source surfaces.
- Redesign Reference Library default path from raw table to source-browser:
  layer summary, search/filter, document list, selected preview, collapsed raw
  source map.
- Rework Owners & TTP as selected-detail workspace and collapse full audit
  matrix/source tables by default.
- Tighten Theory default hierarchy around notation plus Highlighted notation,
  then group control cards by runtime phase.
- Convert Architecture runtime notes and source-boundary prose into compact
  support/disclosure so the primary map remains visually dominant.
- Add a docs/index visual QA runbook with required desktop and narrow browser
  screenshots.

### P2

- Consolidate legacy versioned CSS classes once behavior is stable.
- Add optional ignored screenshot capture helper for repeatable local evidence.
- Add small component examples or fixtures for docs/index tab surfaces.
- Consider a multi-surface design picker only as a tiny local docs/index pattern
  gallery, not as an agent marketplace.
- Improve narrow navigation ergonomics after the P1 layout hierarchy is stable.

## Design-system additions

### `docs/index/DESIGN.md`

- Add a component role matrix: focal display, control selector, support panel,
  provenance/source map, raw data table, disclosure, and generated snapshot.
- Add per-tab focal hierarchy:
  - Architecture: runtime map plus selected-primary carousel.
  - Owners: selected operator/family workspace.
  - Theory: notation map plus Highlighted notation.
  - Reference: source-browser summary/list/detail.
- Add thresholds for progressive disclosure: large source maps, matrices, and
  tables should default to collapsed or secondary placement unless the tab's
  explicit purpose is raw audit review.
- Add examples of good dense UI: vertical lists, selected-detail panes, local
  scroll, grouped controls, and summary-before-table.

### `tools/check_docs_index_interactions.py`

- Keep existing carousel, Theory interaction, token-boundary, and source-parity
  checks.
- Add non-brittle guards for:
  - declared surface roles on major blocks;
  - Reference raw source table not first/default dominant;
  - Owners full matrix/source tables behind support disclosure;
  - source-derived summary counts matching generated data;
  - card/control buttons remaining real interactive controls.
- Avoid pixel-perfect tests. Check structure, source ownership, and interaction
  affordances.

### Visual QA runbook

- Add desktop and narrow local browser passes for Architecture, Owners, Theory,
  Reference, and Boundaries.
- Record what to inspect: focal object, table dominance, wrapping, focus states,
  keyboard path, reduced-motion, selected card/panel behavior, and no
  page-wide overflow.
- Treat "checks passed" as necessary but not sufficient for visual sign-off.

### Optional screenshot regression plan

- Use local-only ignored screenshots for evidence, not release artifacts.
- Capture stable named states rather than comparing pixels:
  - Architecture initial and one carousel advance.
  - Owners selected operator and collapsed audit tables.
  - Theory selected notation/card.
  - Reference selected document and filtered list.
  - Narrow/mobile versions of the same.

## What not to do

- Do not collapse all notation into giant tables.
- Do not use horizontal chip streams for dense pipelines.
- Do not turn carousel previews into label-only tiles.
- Do not hide broken design behind passing structural checks.
- Do not import external design systems as dependencies.
- Do not hand-edit `docs/index.html` or `docs/daee-epistemics-pipeline.html`.
- Do not move runtime semantics into `DESIGN.md`.
- Do not make every card full-width when the intended pattern is selected-primary
  display.
- Do not let provenance/source-owner tables dominate the default reading path.
- Do not replace source-owned generation with parallel hardcoded strings.
- Do not add pixel-perfect tests that make harmless responsive changes painful.

## ACID / SSOT / GRASP guardrails

- ACID: every UI refinement should edit source owners, regenerate HTML, and run
  checkers as one coherent transaction. No partial generated-HTML mutation.
- SSOT: visual tokens and component roles belong in `DESIGN.md`; runtime meaning
  belongs in `runtime-architecture.json` and atomics/runtime owners; generated
  docs are artifacts.
- GRASP Information Expert: `DESIGN.md` owns visual rules, the generator owns
  generated output, runtime JSON/atomics own runtime meaning, and the checker
  owns regression prevention.
- GRASP High Cohesion / Low Coupling: keep layout rules in docs/index design and
  templates, not scattered across runtime docs.
- GRASP Protected Variations: future UI changes must not silently break
  carousel interaction, Theory card mapping, owner catalogue parity, or Reference
  source ownership.

## Release impact

This refinement plan does not currently block v0.4.2.0.

The existing docs/index is safe enough as a source-aware generated navigation
surface: build/check passes, generated HTML is not canonical, and no P0 visual
failure was observed. The P1 items should be addressed before positioning the
site as a polished public design surface or before using docs/index as the main
release presentation layer.
