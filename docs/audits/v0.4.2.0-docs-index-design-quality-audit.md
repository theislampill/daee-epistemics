# docs/index Design Quality Audit

Scope: docs/index visual and interaction discipline. This audit does not migrate runtime
semantics, catalogue ownership, smoke evidence, release assets, or heuristics/noetic-profile
catalogues.

## Executive verdict

TARGETED DESIGN DISCIPLINE NEEDED

The current docs/index system already has a source-owned DESIGN.md, generated HTML, a runtime
architecture source, and structural interaction checks. The remaining risk is not absence of a
system; it is agent drift: future passes can satisfy source/freshness checks while making the
page cramped, generic, visually inconsistent, or interaction-regressing. The fix is targeted
discipline: keep the existing docs/index system, add practical visual rules, and harden the
checker only where the regression class is structural rather than pixel-perfect.

## awesome-design-systems

The repo's README defines a design system as documentation on principles and best practices,
usually embodied in UI/pattern libraries but able to extend to voice and tone. Its tag matrix
classifies systems by Components, Voice & Tone, Designers Kit, and Source code, with a note that
design systems, UI libraries, and pattern libraries often overlap.

Implication for docs/index: maturity is coverage breadth plus source traceability. A serious
docs/index surface cannot stop at a palette and a few classes. It needs:

- components: carousel, cards, tabs, tables, notation chips, details panels, focus states;
- voice/tone: concise labels, source-bound wording, no marketing filler, no proof-by-style;
- source code: generated HTML from docs/index sources and checker-reviewed constants;
- documentation principles: source owners, generated/canonical boundary, visual QA checklist;
- accessibility: keyboard, focus, reduced motion, contrast, wrapping and overflow control;
- layout patterns: selected-primary carousel, dense side-by-side technical panels, progressive disclosure.

Most relevant models for dense docs/index UI:

- Carbon / IBM: enterprise density, data views, accessibility, source-backed components.
- Material: component states, motion boundaries, responsive layout, interaction affordances.
- GOV.UK: clarity, accessibility, content discipline, service-oriented pages.
- Primer: developer documentation, code-oriented surfaces, compact components.
- Polaris: admin/workflow density and content guidance for operational interfaces.
- Fluent: productivity UI, cross-platform interaction consistency, accessibility.
- Atlassian: dense product UI, content guidance, component consistency, documentation.

The lesson is not to borrow their look. It is to borrow the idea that a design system must cover
component behavior, written guidance, source ownership, and verification together.

## Kami

Kami's README frames "paper" as the surface where finished ideas land. Its design docs then turn
that into constraint language: one accent, warm neutrals, fixed type/line-height ranges, spacing
scale, component recipes, print/render pitfalls, and explicit anti-patterns.

Practical takeaways:

- Agent output drifts when the design system is vague. "Modern", "clean", and "professional" are
  not constraints.
- Constraints need numbers, forbidden patterns, and QA steps: line-height ranges, wrapping rules,
  shadow limits, fixed chart/container heights, and render checks.
- A small system can be effective if it is strict at the points agents usually improvise.
- Anti-patterns should name the failure directly: filler content, fake metrics, decorative charts,
  generic gray visuals, hard shadows, overloaded accents, labels that do not carry meaning.

For docs/index, the Kami lesson becomes:

- Do not accept generic gray, unstructured, all-card UI just because it passes generated-file checks.
- Keep an intentional console identity: dark technical surface, stage colors, bounded cards,
  readable notation, and source-owned tokens.
- Use constraint language in AGENTS.md and DESIGN.md so future Codex passes have a bar to hit.

## html-anything

html-anything's README says the generated HTML is what humans read, with Markdown as a draft and
a local agent producing ship-ready single-file HTML. The repo backs that with a template picker,
skill folders, real example.html previews, sandboxed iframe preview, export/screenshot paths, and
hard constraints inside SKILL.md files.

Borrow now:

- Sandboxed preview discipline: docs/index changes need a browser pass, not only Python checks.
- Skill/template surfaces: docs/index should treat each major tab/interaction as a surface with a
  target shape and examples, even though this repo should not create a template marketplace.
- Examples: carousel and dense notation regressions should be guarded by concrete expected
  structures, not generic "looks good" prose.
- Preview/export discipline: visual work is not done until the generated HTML is viewed locally.
- Agent-driven HTML but human-readable output: generated HTML must be readable as a public page;
  checker pass is necessary but not sufficient.
- Multi-surface picker idea: useful as a mental model for docs/index tabs. Each surface has a
  specific layout contract; Architecture, Theory, Owners, Reference, and Boundaries must not all
  collapse into the same card stack.

Too large or irrelevant:

- Local agent CLI detection, SSE streaming, export adapters, template marketplace, Remotion/
  Hyperframes, and its 75-skill catalogue are product architecture, not docs/index needs.
- This repo should not vendor html-anything or adopt its app stack.
- docs/index should keep its generated source model rather than becoming an agentic editor.

## docs/index design-quality rubric

Run this rubric before declaring docs/index visual work complete:

1. One primary focal object per section. The Architecture tab starts with the runtime map; the
   selected Architecture carousel card is the focal object; Theory uses the highlighted notation
   panel as the contextual focal object.
2. No cramped card layouts. A dense grid is allowed only when each card has stable width,
   readable line-height, and enough internal rhythm to scan.
3. No clipped content. Cards, previews, code, notation chips, tables, and source paths must wrap,
   scroll locally, or disclose progressively.
4. No page-wide horizontal overflow. Tables may scroll inside their own container; the page itself
   must stay contained.
5. Dense notation must wrap or disclose progressively. Long formulas, source paths, target
   grammars, and owner lists need wrapping, contextual chips, or collapsed metadata.
6. Provenance/source-owner material should be contextual or collapsed, not dominant. Source maps
   and owner tables are support surfaces, not the default reading path.
7. Interactive cards must remain interactive. Any visual refactor must preserve buttons, click
   targets, keyboard focus, ARIA state, active styling, and linked detail panels.
8. Carousel must be selected-primary, not a scroll rail. One card is readable; neighbors are
   previews and controls select the primary card.
9. Side carousel cards must be scaled previews, not label tiles or clipped fragments.
10. Keyboard/focus/reduced-motion/accessibility pass required. Include tab order, arrow navigation,
    visible focus, aria-selected/aria-pressed, contrast, and prefers-reduced-motion.
11. Local browser screenshot pass required before declaring visual work done. Structural checks
    do not prove the page is visually acceptable.
12. Generated HTML is not canonical. Edit docs/index sources, generator, DESIGN.md, or checker;
    rebuild generated HTML.
13. Design tokens own visuals, not runtime semantics. Runtime meaning remains in atomics,
    docs/index/runtime-architecture.json, and checker-covered source owners.

## Design gates for future work

- DESIGN.md token/source-boundary pass: changed visuals must map to source-owned tokens or an
  intentional local component rule; no runtime meaning moves into DESIGN.md.
- Nielsen-style heuristic pass: visibility of system status, match to user mental model,
  user control, consistency, error prevention, recognition over recall, flexibility, aesthetic
  minimalism, recovery, and help/documentation.
- WCAG/accessibility pass: keyboard, focus, semantics, contrast, reduced motion, responsive text
  and no trapped interaction.
- Dense-interface pass: notation, source paths, formulas, tables, and chip groups wrap or disclose.
- Local browser visual regression pass: view desktop and narrow widths locally before claiming done.
- Poka-yoke checker update: if a regression is fixed, add a structural checker for that exact
  regression class when the signal is non-brittle.

## Remaining caveats

- The checker can catch structural regressions, not taste. A browser visual pass remains mandatory.
- docs/index still contains large reference/provenance surfaces; they are acceptable when scoped to
  support tabs, collapsed metadata, or contextual panels, not as default Architecture/Theory reading.
- No pixel-perfect tests are recommended. The durable bar is: readable, source-bound,
  interaction-preserving, accessible, and locally previewed.
