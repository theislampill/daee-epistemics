## 5 Whys Root-Cause Synthesis Before CI

This section is a pre-CI constraint. It connects Conway/YAGNI findings to automation design so CI
does not automate accidental structure, checker sprawl, generated-runtime ambiguity, or release
process debt.

### 1. Root `SKILL.md` Exceeded the Control-Plane Drift Budget

- Immediate symptom: `atomics/skill/SKILL.md` exceeded 50,000 chars after banner and algebraic-control
  hardening.
- Five Whys:
  1. Why? Detailed banner, source-request, authority-frame, state, and algebraic-control rules were
     placed in the always-read root surface.
  2. Why? The root was treated as the safest place to force runtime behavior after a live smoke
     failed.
  3. Why? Behaviorally unavoidable rules felt more urgent than owner placement during the patch loop.
  4. Why? The repo had strong owner files but no immediate red light until metacompliance measured
     root bloat.
  5. Why? CI/design pressure favored "make the model see it" over "make the right owner own it" when
     closing a regression.
- Root cause: control-plane urgency overrode owner-local DRY discipline.
- Conway implication: root `SKILL.md` was starting to mirror recent conversation pressure rather
  than stable runtime architecture.
- YAGNI implication: long repeated detail in the root did not add a new invariant; it duplicated
  owner contracts.
- CI implication: CI should enforce the drift budget and root required-token anchors, not permit
  root bloat as a workaround.
- Recommended action: CI should enforce.

### 2. Banner / Source-Request / Authority-Frame / State Terminology Duplicated Across Owners

- Immediate symptom: the same banner vocabulary and state semantics appeared in root, render
  contract, output-release, recursive-state, compiler preamble, render checker, and generated
  runtime.
- Five Whys:
  1. Why? The banner had to become behaviorally unavoidable after the smoke omitted it.
  2. Why? Render shape, release semantics, recursive closure, and compiled runtime each needed a
     reference to the same vocabulary.
  3. Why? There was no single exported constant or source prose block consumed by all layers.
  4. Why? The repo uses source prose plus generated runtime rather than a central schema module for
     render vocabulary.
  5. Why? Schema-light governance intentionally avoids hard runtime fields unless explicitly
     authorized.
- Root cause: one conceptual contract crosses render, release, recursion, and generated-runtime
  layers, but no small SSOT bridge exists yet.
- Conway implication: communication boundaries are valid, but terms can drift when every context
  repeats them manually.
- YAGNI implication: do not add a schema migration merely to remove prose duplication; first keep
  one prose owner and short references.
- CI implication: CI should enforce presence/absence of tokens and banned vocabulary, but should not
  force a hard schema migration.
- Recommended action: DRY/SSOT source relocation now; deeper helper extraction deferred.

### 3. Generated `skill/**` Risks Looking Like Quasi-Source

- Immediate symptom: generated runtime files contain rich prose, compiled bundles, scripts, data,
  and tests, making them visually resemble editable source.
- Five Whys:
  1. Why? The compiled skill must be self-contained for package/runtime use.
  2. Why? Omnibus and runtime bundles copy source identity into generated outputs.
  3. Why? Maintainers need generated runtime available for package-shape and release checks.
  4. Why? The repo tracks generated runtime to make package state inspectable.
  5. Why? Without tracked generated runtime, agents could not audit release/package state locally.
- Root cause: tracked generated runtime is necessary for release visibility but naturally creates a
  second readable hierarchy.
- Conway implication: generated `skill/**` mirrors runtime packaging architecture, not source
  ownership; this must stay explicit.
- YAGNI implication: do not delete generated runtime before release just because it looks redundant.
- CI implication: CI should enforce freshness, package boundary, and no hand-edit drift; it should
  not remove `skill/**` in this release line.
- Recommended action: CI should enforce.

### 4. Banner Checker Was Promoted in Prose but Untracked/Ambiguous

- Immediate symptom: `AGENTS.md` referenced `tools/check_noetic_field_banner_samples.py` while the
  checker was initially untracked.
- Five Whys:
  1. Why? The checker was created during a regression loop as a local poka-yoke.
  2. Why? The first concern was proving the failure could not pass locally, not deciding repo
     lifecycle.
  3. Why? Retained smoke artifacts are ignored, so the checker felt local even though the invariant
     is repo-level.
  4. Why? The repo distinguishes static checks, local smokes, dev-local checkers, and package proof.
  5. Why? The promotion boundary was not decided at checker creation time.
- Root cause: evidence-class separation was correct, but the tool lifecycle decision lagged behind
  the AGENTS reference.
- Conway implication: prose governance cannot point at an untracked enforcement tool.
- YAGNI implication: track the checker, but do not require ignored smoke paths in default CI.

### Post-Conway/YAGNI CI Constraints

1. Risks CI should enforce:
   - root `SKILL.md` drift budget and required current-canon anchors;
   - generated runtime freshness from atomics;
   - package boundary and excluded roots;
   - render/banner invariants and banned depth-license vocabulary;
   - routing parity, recursive traversal governance, IR integrity, encoding, frontmatter, and
     release-marker sweeps;
   - py_compile for tracked checker tools, including dev-local tools.
2. Risks CI should not enforce because they are design/policy decisions:
   - whether to hard-migrate schema-light registers into mandatory fields;
   - whether to delete or archive historical docs;
   - whether to consolidate child-mode checker helpers before a drift bug appears;
   - whether generated `skill/**` should become untracked in a future architecture.
3. Risks solved by DRY/SSOT source relocation:
   - banner vocabulary and render requirements: `diagnostic-render-contract.md`;
   - release state semantics: `output-release.md`;
   - `Delta-nB`, `Delta-kappa`, `kappa/H`, and reread control:
     `recursive-state-transitions.md`;
   - package boundary enforcement: `tools/check_package_shape.py` plus
     `docs/source-vs-runtime-layout.md` for prose.
4. Risks solved by release artifact automation:
   - package SHA/size/entry-count coherence;
   - release asset metadata and release-artifacts docs;
   - current-release smoke provenance tied to package filename and SHA;
   - tag/release absence or intended replacement checks.
5. Risks deferred to post-release cleanup:
   - checker helper extraction;
   - docs/index POUR/accessibility pass;
   - historical docs status/index labeling;
   - optional dev-artifact split for harness scripts/data/tests;
   - verification runner design.
6. Risks that would get worse if CI automation is added too early:
   - freezing incident-specific checker sprawl as permanent CI architecture;
   - treating ignored local smokes as package/release proof;
   - making historical docs look current by sweeping them mechanically;
   - adding hard schema/register fields just to simplify checks;
   - requiring generated `skill/**` deletion before the release-line packaging decision.

The later GitHub CI/release-automation audit must use these constraints: enforce stable
invariants, freshness, package boundaries, and release provenance; do not automate unresolved
architecture decisions or prompt-specific regression stories as if they were runtime doctrine.
